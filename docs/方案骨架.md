## 1. 项目背景

- 赛道：GOAI 世界人工智能开源大赛 · Agent Infra（新智基座）
- 方向：方向一 零人工运维

## 2. 核心命题

**数据库运维是"零人工运维"最难的领域**：

- 有状态系统，变更难以回滚（改错参数会雪崩、DDL 会锁表、数据改错回不来）
- 根因链深：慢 SQL → 锁等待 → 连接池打满 → 应用超时，现象与根因隔着多层
- 全场评委的直觉都是"不敢让 AI 动生产数据库"

**方案定位**：用「备节点先验 + JIT 权限 + 分级授权」三重保险，回答"敢"。

**差异化**（vs 通用运维方案）：

1. 数据库领域存在"廉价的真实验证手段"（三节点备库），这是通用运维没有的
2. 备节点验证 + 滚动变更，本来就是 DBA 的真实操作套路，一线说服力更强
3. Higress `allowedConsumers` 秒级授权/吊销，用在数据库上是杀手级能力

## 3. 总体架构

```
┌─────────────────────────────────────────────────────────┐
│  AgentTeams（多 Agent 协同底座，必选）                     │
│  Manager → Team Leader → Workers                        │
│  Matrix Rooms（通信/审计）· MinIO（共享状态）              │
└──────────────────┬──────────────────────────────────────┘
                   │ Higress AI Gateway
                   │（凭证集中管理 · Worker 只持工牌）
┌──────────────────┴──────────────────────────────────────┐
│  阿里云 Skills 门户（官方云 Skills，只读/诊断权限）          │
│  aliyun CLI / MCP → 阿里云 OpenAPI                       │
└──────────────────┬──────────────────────────────────────┘
                   │
┌──────────────────┴──────────────────────────────────────┐
│  ECS × N（PostgreSQL 三节点数据库）                         │
│  阿里云可观测（云监控 CMS · 日志 SLS · AgentLoop）          │
└─────────────────────────────────────────────────────────┘
```

**关键设计**：

- 所有 Agent 通过 Higress 网关访问阿里云 OpenAPI / MCP，凭证集中在网关，Worker 只持 Consumer Token
- 官方云 Skills 默认只读/诊断权限，天然符合安全边界
- Matrix Room 即故障处置的完整审计轨迹
- MinIO `shared/tasks/task-{id}/` 存放诊断证据、沙箱报告、执行记录，避免大上下文塞进 token

## 4. AgentTeams 能力映射表

评审明确："不是只看是否提到工具名称"。逐条对齐框架真实机制：

| 赛道要核验的能力 | AgentTeams 真实机制 | 本方案用法 |
|---|---|---|
| 角色编排 | Worker/Team/Human/Manager 四种 CRD（agentteams.io/v1beta1），agt apply 声明式下发 | 每个 Agent 一份 Worker CR，soul 写 DBA 人格，skills 挂数据库 Skill |
| 任务拆解 | Manager → Leader → Worker 三级委派，Manager 不入 Team Room | Manager 收敛告警成工单派给 Lead，Lead 拆成诊断/预案/验证/执行子任务 |
| 上下文传递 | MinIO shared/tasks/task-{id}/ 的 meta.json / spec.md / result.md + Matrix 消息 | 故障工单即 task-id，诊断证据/沙箱报告/执行记录落同一目录 |
| 协同执行 | Leader Room / Team Room / Worker Room / Leader DM 四类房间拓扑，peerMentions + m.mentions | Team Room = 故障应急群，DBA 全程旁观 |
| 状态追踪 | Controller Reconcile Loop + heartbeatEvery + Manager 心跳 | 处置状态机；Agent 卡死由 Manager 自动上报 |
| 人工审批 | Human CRD 三级权限 + Room 内实时 @mention 介入 | L3 高危变更强制 DBA 在 Room 内确认 |
| 审计 | Matrix 消息天然持久化 | 一次处置的完整对话即审计轨迹，零额外成本 |

## 5. Agent 分工

**1 Manager + 6 Workers**：

| 角色 | AgentTeams 身份 | 职责 | 权限边界 |
|---|---|---|---|
| db-oncall-manager | Manager CR | 多源告警接入与收敛去噪、派单、心跳监控 | 无数据库凭证 |
| db-oncall-lead | Worker，role=team_leader | 工单拆解、子任务编排、多方案择优、风险分级决策、结论汇总 | 无数据库凭证 |
| db-diagnostician | Worker | 根因定位：慢 SQL、锁等待链、资源瓶颈、执行计划突变 | 只读 MCP |
| db-planner | Worker | 生成 N 个候选修复预案 + 回滚方案 + 风险自评 | 无执行权 |
| db-sandbox-validator ★ | Worker | 备节点上验证候选变更，产出实测数据 | 仅备节点写权 |
| db-executor ★ | Worker | 生产执行 + 恢复验证 | JIT 写权，用后即焚 |
| db-retrospector | Worker | 复盘报告、经验沉淀为 Skill / 写回知识库 | 只读 + 知识库写 |

**设计要点**：

- planner 只生成不验证、validator 只验证不决策、lead 只决策不执行——「生成—验证—择优」三角，命中评审"是否能处理异常、冲突和多方案选择"
- db-sandbox-validator 的差异化：**备节点验证 + 滚动变更**，而非克隆实例。三节点架构下，先在备库验证变更、再滚动到主库，是 DBA 的真实操作套路，比"克隆实例"更贴近现有能力，也更具一线说服力

### 6.2 自研 Skills（详细展开 5 个）

1. **db-alert-correlate** — 多源告警按实例/集群/根因链聚合，抑制告警风暴
2. **db-jit-grant** — 对接 Higress allowedConsumers 的授予与回收 ★★安全核心
3. **db-change-risk-grade** — 按锁范围/影响面/可逆性输出 L0–L3 ★决定是否需人工
4. **db-plan-baseline-diff** — 执行计划与历史基线比对，定位计划突变 ★数据库特有
5. **db-standby-validate** — 备节点验证变更，输出实测耗时/锁等待/副作用 ★★核心

**复用价值论证**：这些 Skill 不绑定业务，任何跑 PostgreSQL 的团队都能直接用。

## 10. 风险分级 = "零人工"的量化定义

"零人工运维"不是"完全无人"，而是**把人从执行环节移出，只保留在授权环节**：

| 级别 | 动作类型 | 授权策略 |
|---|---|---|
| L0 | 只读诊断 | 全自动 |
| L1 | 无状态干预（kill 会话、限流、切读写分离流量） | 自动执行 + 事后通报 |
| L2 | 可逆变更（参数调整、加索引） | 备节点验证通过 → Lead 批准 → Room 内超时未否决即放行 |
| L3 | 不可逆（DDL、数据修正、主备切换） | 强制人工 Room 内确认 |

**核心指标**：人工介入率 = 1 − (L0+L1+L2 自动放行) / 全部告警

**初赛量化目标**：

- 人工介入率 ≤ 40%（即 L0+L1+L2 自动处置覆盖率 ≥ 60%）
- 告警收敛比 ≥ 3:1（100 条原始告警收敛为 ≤ 33 个工单）
- MTTR 改善 ≥ 30%（相比纯人工处置基线）
